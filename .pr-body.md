## Summary

- Added `hooks/hooks.claude.json` — the same two hooks (`pre-push-guard` PreToolUse(Bash), `subagent-gate-guard` SubagentStop) in Claude Code's exec `args` array form (`"command": "bash", "args": ["${CLAUDE_PLUGIN_ROOT}/hooks/<script>.sh"]`), confirmed against the live Claude Code hooks docs to support `${CLAUDE_PLUGIN_ROOT}` substitution inside `args` entries with no shell involved.
- Renamed `hooks/hooks.json` → `hooks/hooks.codex.json` and pointed `.codex-plugin/plugin.json` at it. **Review caught a double-fire bug in the first version of this change**: Claude Code's plugin manifest schema documents "own merge rules" for the `hooks` field, and empirically an explicit `hooks` key in `.claude-plugin/plugin.json` loads ADDITIVELY alongside the conventional `./hooks/hooks.json` path rather than replacing it — so the first cut (explicit `hooks.claude.json` key + Codex left at the conventional `hooks/hooks.json` path) would have made Claude Code fire every hook twice. Renaming the Codex file off the conventional path empties it, so CC's conventional-path scan finds nothing and only `hooks.claude.json` loads. Verified separately that Codex replaces its default `hooks/hooks.json` discovery whenever `.codex-plugin/plugin.json` declares an explicit `hooks` entry, so pointing it at `hooks.codex.json` carries no equivalent risk on that side.
- Added `tests/hooks-harness-split.test.sh`: asserts the conventional `hooks/hooks.json` path does not exist (regression guard against the double-fire recurring), each manifest points at its own renamed hooks file, `hooks.claude.json` is exec-args-form only (no shell-string commands, every entry has `args`), no `${user_config.*}` leaks in, and both hooks files declare the same events, the same matchers per event, and the same target scripts so they can't drift silently.
