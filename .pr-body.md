## Summary

- `otta-release-setup.sh` now **infers** the runner from the repo's existing workflows instead of hardcoding `ubuntu-latest`. The repo already encodes the right answer; this reads it.
- Adds `--runner <value>` to override, and reports the chosen runner and *why* on every path — the silence was the actual bug.
- Generated output is byte-identical to before in the `ubuntu-latest` case, so nothing changes for hosted repos.

## The failure this removes

On a repo that cannot schedule GitHub-hosted runners, the generated job never picked up a runner. Nothing errored:

- setup printed `✓ Installed`
- the workflow file existed and looked right
- tagging simply never happened
- `deploy_tag` never fired, so DORA deployment frequency read **zero** instead of "not instrumented" — otta-build/pulse#153

Concrete case: **otta-build/pulse**, a private repo in a free org with hosted minutes exhausted, whose three workflows all use `[self-hosted, linux]`.

Per the universal-multi-team-tool directive this is not only our problem — any customer installing Otta on a private repo, a self-hosted fleet, or ARM/large runners hit the same silent no-op.

## Notes

Argument parsing became a loop to take `--runner`, so `--dry-run` is no longer position-dependent and an unknown flag now exits 2 with usage instead of being ignored. Previously only `$1` was inspected, so `otta-release-setup.sh --typo` silently did a real install.

**Rebase note, worth flagging as a real hazard.** This branch was rebased onto #191 and the `merge=ours` driver silently replaced this `.pr-body.md` with **main's** copy — during a rebase, "ours" is the *upstream* side, so the body describing #190 landed here. It was caught and rewritten. GitHub does not run custom merge drivers server-side either, which is why the PR showed as conflicted in the first place. The tracked-`.pr-body.md` model has this failure mode inherently; otta-build/dev avoided it by untracking the file (its #78), and whether this repo should follow is the open decision noted in #181.
