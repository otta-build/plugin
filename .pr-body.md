## Summary

- Verified against gemini-cli source (v0.52.0, `packages/core/src/telemetry/sdk.ts` + `config.ts`) that Gemini CLI exports OTLP **directly** — no collector sidecar is required for `telemetry.target: "local"` (the default). The previous script's collector-sidecar approach was based on an incorrect premise.
- Auth headers ARE supported: Gemini's OTLP exporters are constructed with only a `url` (no explicit `headers`), so `@opentelemetry/otlp-exporter-base` falls back to the standard `OTEL_EXPORTER_OTLP_HEADERS` env var.
- Discovered and fixed a second gap: Gemini's folder-trust feature (default ON) silently drops workspace-scoped `.gemini/settings.json` — including our telemetry block — unless the folder is trusted. Script now also sets `GEMINI_CLI_TRUST_WORKSPACE=true` (the documented CI/automation bypass), or the config would appear written but never take effect.
- Rewrote `otta-gemini-setup.sh` to write `.gemini/settings.json` (`telemetry.enabled/target/otlpEndpoint/otlpProtocol`) + `.otta/gemini.env` (`OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_RESOURCE_ATTRIBUTES`, `GEMINI_CLI_TRUST_WORKSPACE`) instead of a docker-dependent OTel Collector sidecar; added `--derive` mode matching `otta-codex-setup.sh`.
- QA hardening: an existing `.gemini/settings.json` that's non-empty and either fails to parse as JSON, or parses but isn't a JSON object (array/string/number), now makes the script exit 1 with an error naming the file, writing nothing — instead of silently treating it as `{}` and clobbering the user's config. Empty/absent files still fall back to `{}` unchanged.
